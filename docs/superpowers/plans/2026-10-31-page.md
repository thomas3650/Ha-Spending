# The page – implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the page in Home Assistant's side menu shows the household's spending: screens 1 to 4 of the UI spec, with
every state of its §6 and the accessibility of its §7, the view state in the frame's hash for back (D10), on the
`/api/data` answer of plan 2 (technical spec §11, step 3).

**Architecture:**
- The page is Lit. `<hs-app>` owns one `ViewState`. The state is written to and read from the hash. The app fetches
  `/api/data` for `fetchRange` of the period and holds the answer.
- Pure model functions turn the answer and the state into what each card shows. Every sum, share, average,
  comparison and colour comes from `@ha-spending/shared`. What the page needs and shared lacks is added to shared
  first (Task 1).
- Apache ECharts draws the circle, the bars and the Forskel bars, through one thin wrapper module. It is SVG-rendered
  and `aria-hidden`. Beside each chart, a DOM layer of named buttons, or a table, carries the keyboard, the
  accessible names and the clicks. The tests click that layer. The drawing is checked in Chrome.

**Tech Stack:** as plans 1 and 2 (TypeScript 6.0.3, Lit 3.3.3, Vite 8.3.5, Vitest 5.0.5, happy-dom 21.0.4,
`@testing-library/dom` 10.4.2). New: **`echarts` 6.0.0**. The implementer runs `npm view echarts version` and pins
the latest stable 6.x exactly; `zrender` comes with it.

**Spec:** [UI and UX spec](../specs/2026-10-30-ui-ux-design.md) (all of it; it wins where the two meet), within the
[technical spec](../specs/2026-10-30-technical-design.md) (§1, §4, §6, §7.1, §7.3). The mockups:
[`docs/mockups/v2/`](../../mockups/README.md). Screens 2 and 4 still draw five pieces and Øvrige; the UI spec §3.2
wins. Decisions D10–D18 hold.

## Global Constraints

- Everything in plans 1 and 2's Global Constraints still holds. That covers English everywhere, minimal comments, made-up data
  only, exact versions, and Conventional Commits with `git commit -F <file>` and
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Never on `main`, never `--no-verify`.
- **Danish** only in `addon/web/src/i18n/da.ts`. Tests build every expected Danish string from `da` or from
  `src/format.ts`, as `app.test.ts` does with `da.hello`. A Danish literal in a test is a finding, except in `format.test.ts` and `da.test.ts`, which pin the copy. Firefly III's names in
  fixtures are data (D14).
- **Tests** query by role, accessible name and rendered text (hard rule 5). No CSS selectors, no snapshots, no reading
  ECharts options. `test/setup.ts` keeps failing a test on an unexpected `console.error`.
- **Today:** the app holds one `today`. It starts as `localToday(new Date())` and becomes `answer.today` after
  the answer of each fetch the user started; a retry's answer never moves it. That `today` is the period's, the range's and the timeline's
  (`ViewContext.today`). The rule is pinned in Task 4.
- **Money:** amounts stay integer øre until `format.ts`. `format.ts` divides by 100 and lets `Intl` round (half away
  from zero). Signs:
  - A key number or a circle amount is unsigned: "115.660 kr.".
  - A posting shows spending as minus and a refund as plus, with øre: "-310,12" and "+200,00".
  - A Forskel difference is signed: "+1.938 kr.".
- **Numbers and dates:**
  - Every number goes through `Intl.NumberFormat('da-DK')`. Per cents carry Intl's no-break space ("25\u00a0%").
  - Dates follow the UI spec exactly (controller's ruling).
    - Short month names come without a dot, from `da.months` (`jan feb mar apr maj jun jul aug sep okt nov dec`), never
      from Intl's short month.
    - Ranges are built in `format.ts`: "1. jan – 30. okt 2026", "1. – 31. jul 2026", "1. nov 2025 – 31. okt 2026",
      "30. okt 2026".
    - Long month names ("oktober") and table dates ("26.10.2026") come from `Intl.DateTimeFormat('da-DK',
      { timeZone: 'UTC' })` on `Date.UTC` dates.
- **The look:** a light theme only, with `color-scheme: light`. These tokens, on `:host` in `src/theme.ts`, come from
  `docs/mockups/v2/1-alt-forbrug.html` and `4-soejle.html`:
  - `--hs-bg #f5f5f5`, `--hs-card #fff`, `--hs-line #e3e3e3`, `--hs-soft #f0f0f0`, `--hs-text #1f1f1f`,
    `--hs-muted #6b6b6b`;
  - `--hs-accent #03a9f4`, `--hs-accent-soft #e1f3fd`, `--hs-accent-text #0277bd`, `--hs-chip-x #b3e0fb`;
  - `--hs-field #c9c9c9`, `--hs-grid #ececec`, `--hs-leader #b5b5b5`, `--hs-up #c62828`;
  - `--hs-more #eb6834`, `--hs-less #2a78d6`;
  - `--hs-font: Roboto, "Segoe UI", system-ui, sans-serif`, with a 14 px base size.

  Cards are white, 12 px radius, a 1 px `--hs-line` border and 16 px padding. The page has 16 px × 20 px padding, a
  14 px gap and a max width of 1360 px. The pieces' colours are shared's `PALETTE` and greys. The bars are
  `--hs-accent`, or the chosen category's colour. ECharts reads the tokens with `getComputedStyle` when it renders.
- **Layout:** the key numbers are three equal columns. Below them sit two halves, `minmax(0, 5fr) minmax(0, 7fr)` (the
  mockups' 545 : 760). The halves stack when the frame is narrower than **960 px** (D22).
- **Relative URLs only:** the page fetches `api/data?start=…&end=…`. `scripts/check-dist.mjs` still passes. ECharts is
  bundled from `echarts/core` with only the parts used. Nothing comes from a CDN.
- **Links to Firefly III:** a posting is a link only when `fireflyLinkUrl` parses as an `http:` or `https:` URL. The
  link is `${base without a trailing /}/transactions/show/${encodeURIComponent(groupId)}`, with `target="_blank"` and
  `rel="noopener noreferrer"`. Otherwise the posting is plain text.

## Rulings and decisions (entries for `docs/decisions.md`, Task 12)

- **D19 The charts are drawn by ECharts and named in the DOM.**
  - ECharts uses the SVG renderer: it stays sharp at any zoom, has few elements here, and the build stays small.
  - The chart's element is `aria-hidden="true"`. Beside it, a visually hidden list of `<button>`s carries one button
    per piece and per bar, and a table carries the Forskel rows.
  - Hover or focus on a button calls `highlight` on its piece or bar, so the focus is visible on the chart. Blur
    calls `downplay`.
  - A click on a piece, its ECharts label or a bar calls the same handler as its button.
  - The wrapper `src/charts/echarts.ts` is mocked in the component tests: happy-dom has no canvas, and zrender measures
    text with one.
- **D20 The view state's hash.**
  - The keys are `period`, `from`, `to`, `by`, `accounts`, `group`, `category`, `unit`, `card`, `view`, `q`, `sort`,
    `min` and `max`, in a `URLSearchParams` string.
  - A default value is left out, so the opening view is the empty hash.
  - Uden hovedgruppe and Uden kategori are the key present with an empty value (`group=`). No filter is the key
    absent.
  - All accounts is `accounts` absent, so a new account appears by itself. Ticking every account sets it absent too.
  - A click pushes a history entry, so back steps one click. Typing in the search replaces the entry. Folding a
    group and "Vis ældre" are not in the state.
  - A value that does not parse, or that the answer does not know, falls back. Dates are checked with shared's
    `isDate`.
- **D21 A category implies its main group.** Removing "Hovedgruppe: …" on Alle posteringer also removes the
  category, as a trail link drops the levels below it. Adding a category through "+ Filter" sets its main group.
- **D22 The halves stack below 960 px of frame width.** With Home Assistant's side menu open, a 1280 px window leaves
  the frame about 1024 px. Two halves still fit there, so the 1280 px of UI spec §8 holds.

## Review Focus

- **A today that differs from the add-on's:** the browser's date is past midnight but the add-on's is not (or the
  other way round). The page fetches again once with `answer.today` and shows the add-on's period. It never loops
  (Task 4: when every answer disagrees there are exactly two calls).
- **A stale answer:** the period is changed twice quickly. The first answer arrives last and must not replace the
  second (Task 4: two pending fetches, answered in reverse order).
- **Uden hovedgruppe and Uden kategori as choices:** a click on Uden hovedgruppe opens it, and the hash round-trips
  `group=` as `null`. The trail and the chips name it (Tasks 3 and 9).
- **A chosen unit that no longer exists:** a unit is chosen, then the grouping changes or the period moves. The chip
  goes, Forskel falls back to Søjler, and nothing shows a unit of another grouping (Tasks 3 and 11).
- **An unknown name in the hash:** a main group or a category the answer does not hold, or an account id that is
  gone. The page falls back to the level above, drops the unknown ids (a list that ends up empty stays empty,
  showing no accounts), and replaces the hash (Tasks 3 and 4).

## Spec conflicts ruled here

- **Dates:** technical spec §6 says dates go through `Intl`. The UI spec writes "1. jan – 30. okt 2026", without
  Intl's dots. The UI spec wins (controller's ruling): the short month names come from `da.months`. Intl stays for numbers,
  long month names and table dates.
- **"Every piece … has an accessible name"** (UI spec §7) is met by the DOM layer, not the ECharts SVG (D19).
- **Bookmarks** (UI spec §3.1, §5) fell with D10. Only back works.
- **Today:** technical spec §4 says "the day the data was read". The page uses `answer.today` once it has an answer,
  and the browser's date only for the first fetch.
- **The mockup's footer** on screen 3 names "konto" under "+ Filter". UI spec §4.3 keeps accounts in Konti alone,
  and the spec wins.
- **"1280 px and wider"** (UI spec §8) is the window. Inside the frame the halves stack below 960 px (D22).
- **A part of 0 or less** has no piece (UI spec §2). It is listed as a button under the ring, so it can still be
  opened, and it keeps its Forskel row.
