# The data – implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the add-on reads a household's spending from Firefly III, read only, and serves it on `GET /api/data` in
one typed answer. The money rules the page will need are pure, tested functions in `shared/`. A fake Firefly III
drives the tests and the fast loop, and integration tests prove the fake against a real Firefly III in Docker
(technical spec §11, step 2). The page stays "Hej": plan 3 builds the screens on this.

**Architecture:** `shared/` holds the answer type and the money rules (units, sums, averages, comparisons, the
circle's colours) as pure functions over `YYYY-MM-DD` strings. The server reads Firefly III through a client that has
only `get`. It maps categories to main groups from the rules, turns splits into postings, caches each range for
5 minutes, and maps every Firefly III failure to an error code. A fourth workspace, `dev/`, holds the fake Firefly III
(a Hono app), one fixed example dataset, a seeded generator for the fast loop, and the compose file and seeder for a
real Firefly III. The example dataset is checked twice with the same expected sums: through the fake in `npm test`,
and through the real Firefly III in `scripts/integration`.

**Tech Stack:** as plan 1, no new libraries: TypeScript 6.0.3, Node 24, Hono 4.13.14 + `@hono/node-server` 2.1.5,
Vitest 5.0.5, tsx 4.23.15, `@types/node` 24.19.2. Firefly III `fireflyiii/core:version-6.7.9` in Docker with SQLite.

**Spec:** [technical spec](../specs/2026-10-30-technical-design.md) (§2, §3, §4, §5, §7.1, §7.2, §9, §11 step 2),
within the [UI and UX spec](../specs/2026-10-30-ui-ux-design.md) (§2 the words, §3.1 units, averages and
comparisons, §3.2 colours, §6 states). The Firefly III facts (image digest, headless token, JSON shapes, earliest
posting) are from a spike against Firefly III 6.7.9 on 2026-10-31, copied below. Use them as written. Do not invent
`artisan` commands.

## Global Constraints

- Everything in plan 1's Global Constraints still holds: English everywhere, minimal comments, one source per fact,
  made-up data only, exact versions, Conventional Commits with `git commit -F <file>` and the co-author trailer
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`, never on `main`, never `--no-verify`.
- **Danish:** the page's texts stay in `addon/web/src/i18n/da.ts`, and the option labels go in
  `addon/translations/da.yaml`. Firefly III's own names are data, not page text (D14). That covers the rule group
  `Hovedgrupper`, the main group `Penge ind og ud`, and the categories in the seeds. So they may stand in option
  defaults, fixtures and seeds. No Danish sentence comes from the server or from `shared/`: errors are codes, and
  Uden hovedgruppe and Uden kategori are `null` keys.
- **Read only:** the server's Firefly III client has one method, `get`. Only `addon/dev/` (the seeder) ever sends
  anything but GET to a Firefly III.
- **The token** never appears in an error, a log line, an answer, a file in the repo, or CI output. The fast loop's
  token is the made-up `fake-token`. The integration token lives only in the `scripts/integration` process's
  environment. It is masked in CI, and it is never written to disk or echoed. Never `set -x` in that script.
- **Money:** amounts are integer øre from Firefly III's decimal strings, parsed without floating point. An average is
  `Math.round` of the sum over the count.
- **Dates:** `YYYY-MM-DD` strings everywhere. Date math in `shared/` is UTC on those strings; only `localToday` reads the
  process's time zone, to name today. A Firefly III date is
  its first 10 characters, never passed through `new Date()`. Shared tests run with `TZ=Pacific/Auckland` and server
  tests with `TZ=UTC`, so a date that depends on the machine's zone fails.

  `#2a78d6`, `#eb6834`, `#1baf7a`, `#eda100`, `#e87ba4`, `#008300`, `#6250d6`, `#e34948`. The greys run from

## Rulings and decisions (entries for `docs/decisions.md`, Task 7)

- **D11** The fake Firefly III is a fourth npm workspace, `addon/dev/` (`@ha-spending/dev`). The compose file and
  the token script for the real Firefly III sit beside it in `addon/dev/firefly/`. `scripts/` holds only entry
  scripts (`develop`, `integration`, `setup`, the link check). Spec §2's layout wins over §7.1's "in `scripts/`".
- **D12** Reading Firefly III:
  - The client takes a page size, 500 in the add-on (§3.3), and the integration tests set 5. Paging follows each
    answer's `meta.pagination.total_pages`, so a server-side cap does no harm.
  - The earliest posting date takes two GETs: `limit=1` from `1900-01-01`, then the last page.
  - The answer lists every asset account, active or not, so a filter by account never drops a posting.
- **D13** With `HA_SPENDING_DEV=1` the server binds `127.0.0.1` only, because it now holds a token. In the add-on it
  binds all addresses, as before. The options file is `HA_SPENDING_OPTIONS`, `/data/options.json` by default.
- **D14** Firefly III's own names (rule groups, main groups, categories) are data, not text. They may be Danish in
  option defaults, fixtures and seeds. Hard rule 6 governs the add-on's own words.
- **D15** A posting's `category` is the category's **name**, because the rules match categories by name.
  Uden hovedgruppe and Uden kategori are `null` in `shared/` and the answer. Their texts belong to `da.ts`.
- **D16** The unit rulings, where UI spec §3.1 leaves a choice:
  - **Whole units:** a unit is whole when it is not partial, i.e. not still running on the day the data was read
    (technical spec §4, UI spec §3.1, read plainly; the controller's ruling). A clipped unit at the period's start
    or end is shown clipped, with its clipped sum, but it counts as a whole unit in the averages and comparisons.
  - **One-unit periods:** a period with **at most one** whole unit is a one-unit period. Examples: "Denne måned" by
    Måned on 30 Oct has none; 1 Sep–30 Oct by Måned has one.
  - **The unit compared:** the last whole unit; with none, the last unit.
  - **Units before the data:** a unit whose last day is before the earliest posting has no data. It is left out of
    every average and makes a comparison `null`.
  - **Colours:** they are given from the period's totals, so a part keeps its colour when a unit is chosen.
    - Positive parts in circle order take the palette, then n greys, `round(138 + 58·i/(n−1))` per channel (one grey
      alone is `#8a8a8a`).
    - Parts of 0 or less get `#c4c4c4` and no piece.
- **D17** The integration Firefly III's user and token come from a PHP bootstrap script run inside the container. The
  image has no `tinker`, and `system:create-first-user` refuses outside testing. The token stays in the test run's
  environment.
- **D18** `/api/data` answers errors as codes:
  - Firefly III unreachable, timed out, answering 5xx or not JSON: `502 {"error":"unreachable"}`.
  - Firefly III answering 401 or 403: `502 {"error":"refused"}`.
  - A bad query: `400 {"error":"bad-request"}`.
  - Anything else: `500 {"error":"internal"}`.

  The page shows "Firefly III svarer ikke" or "Firefly III afviser nøglen" from these codes (plan 3).
- Node 24 stays (D4), against the spec's Node 22.

## Review Focus

- **Summer-time dates in a UTC container:** Firefly III answers `2026-07-01T00:00:00+02:00`. The posting's date must
  be `2026-07-01`, not 30 June. Task 4 tests this in `TZ=UTC`, and the fake emits `+02:00` in summer (Task 3).
- **A posting on an inactive account:** the account must still be in `accounts`, or a filter by ticked accounts
  drops the posting and the sums stop adding up (Task 4: an inactive account in the example dataset).
- **An empty Firefly III:** no transactions gives `total_pages` 0. The answer is `earliestPostingDate: null` and
  `postings: []`, with no crash. `keyNumbers` then gives an average of `null` and no comparison (Tasks 2 and 4).
- **A `firefly_url` that answers HTML** (Firefly III's web page, or a proxy's login page) with 200: the answer must
  be `unreachable`, not a 500 or a crash (Task 4).
- **A Firefly III that caps `limit`** below what was asked: every page must still be read (Task 4: the fake capped at
  3 per page returns all 16 groups).

export type Grouping = 'day' | 'week' | 'month' | 'quarter' | 'year';
export interface Unit {
  start: string; end: string;          // clipped to the period
  fullStart: string; fullEnd: string;  // the whole calendar unit (ISO week: Monday–Sunday)
  partial: boolean;                    // fullStart <= today <= fullEnd, or the unit lies after today
  clipped: boolean;                    // start !== fullStart || end !== fullEnd
}
export interface Timeline { period: Period; grouping: Grouping; today: string; earliest: string | null }
export function unitAt(date: string, grouping: Grouping, today: string): Unit          // unclipped
export function unitBefore(unit: Unit, grouping: Grouping, today: string): Unit       // the full unit before fullStart
export function unitsOf(period: Period, grouping: Grouping, today: string): Unit[]    // oldest first
export function isWhole(unit: Unit): boolean                                           // !partial; a clipped unit is whole (D16)
export function hasData(unit: Unit, earliest: string | null): boolean                  // earliest !== null && fullEnd >= earliest
export function isOneUnit(period: Period, grouping: Grouping, today: string): boolean // at most one whole unit (D16)
export function fetchRange(period: Period, grouping: Grouping, today: string): Period
```

  `fetchRange`: `end` is `period.end`. `start` is the `fullStart` of the unit 12 units before the period's first
  unit for a one-unit period, else the `fullStart` of the unit just before the period's first unit. That covers the
  unit before the last whole unit, and the unit before any chosen unit.

export interface ClassifiedPosting extends Posting { mainGroup: string | null }
export type Level =
  | { kind: 'all' }                                              // parts: main groups
  | { kind: 'mainGroup'; mainGroup: string | null }              // parts: categories
  | { kind: 'category'; mainGroup: string | null; category: string | null };  // no parts
export interface Part { key: string | null; amount: number }    // null: Uden hovedgruppe / Uden kategori
export interface Average { amount: number | null; units: number; basis: 'period' | 'before' }
export interface Comparison { unit: Unit; amount: number; before: Unit; beforeAmount: number | null }
export interface KeyNumbers { total: number; average: Average; comparison: Comparison | null }
export interface ChosenNumbers { amount: number; average: Average; before: Unit; beforeAmount: number | null }
export interface Difference { key: string | null; amount: number; average: number | null; difference: number | null }

export function classify(postings: Posting[], categories: Category[]): ClassifiedPosting[]
export function select(postings: ClassifiedPosting[], level: Level, accounts: ReadonlySet<string> | null): ClassifiedPosting[]
export function within(postings: ClassifiedPosting[], range: Period): ClassifiedPosting[]
export function total(postings: ClassifiedPosting[]): number
export function parts(postings: ClassifiedPosting[], level: Level): Part[]   // parts present in postings, by key
export function share(amount: number, whole: number): number | null          // a fraction; null when whole <= 0
export function unitTotals(postings: ClassifiedPosting[], units: Unit[]): number[]   // per unit, by start..end
export function keyNumbers(postings: ClassifiedPosting[], t: Timeline): KeyNumbers
export function chosenUnitNumbers(postings: ClassifiedPosting[], t: Timeline, chosen: Unit): ChosenNumbers
export function differences(postings: ClassifiedPosting[], level: Level, t: Timeline, chosen: Unit): Difference[]
```

  `postings` in the last three are the selected postings of the whole fetched range (`fetchRange`). Each function
  filters to the period itself where a number is the period's.
  - **`keyNumbers`:** `total` is the period's.
    - The average: with `isOneUnit`, basis `'before'` over the 12 full units before the period's first unit that
      have data. Otherwise, basis `'period'` over the period's whole units that have data. With 0 units the amount
      is `null`.
    - The comparison: the last whole unit, or with none the last unit, against `unitBefore` of it. `beforeAmount`
      is `null` when that unit has no data. The comparison is `null` only when the period has no units.
  - **`chosenUnitNumbers`:** the chosen unit's sum, within the period, against the average of the other whole units
    with data in the period, or for a one-unit period the `'before'` average. Also against `unitBefore`.
  - **`differences`:** one row per part of the period's postings at `level`. `amount` is the chosen unit's part,
    `average` the part's average on `chosenUnitNumbers`' basis, and `difference = amount − average` (`null` when
    the average is `null`). Rows are sorted by `|difference|` descending, then key; rows with a `null`
    difference come last.

- **The client:**
  - It sends `GET ${baseUrl}/api/v1/${path}?…` with `Authorization: Bearer <token>` and
    `Accept: application/vnd.api+json`, and returns the parsed JSON.
  - 401 or 403 is `refused`.
  - A network error, an abort, 5xx, any other non-2xx, a non-JSON body, or JSON with no `data` is `unreachable`.
  - The client object has `get` and nothing else.
- **`getAllPages`** adds `limit` and `page` and reads pages one after another until `page >= total_pages` from each
  answer. It returns all `data[]`.
- **`toOre`** parses sign, integer and fraction digits as strings, then rounds half away from zero at the third
  decimal.
- **`mapCategories`:**
  - Rules are sorted by `attributes.order`, and inactive rules, triggers and actions are skipped.
  - Each `category_is` trigger × `add_tag` action pair sets the category's main group, and the later one wins.
  - `conflicts` lists each category mapped to two different main groups, once.
- **`toPostings`** keeps the order of these steps:
  1. The main group of the split's `category_name` comes from `mainGroupOf`.
  2. A split whose main group is in `excluded` is dropped.
  3. A `withdrawal` with `source_type` `Asset account` is `spending`, on `source_id`.
  4. A `deposit` with `destination_type` `Asset account` and a category is a `refund` (negative), on
     `destination_id`.
  5. Everything else is dropped.

  The date is `date.slice(0, 10)`, and `text` is `description`. Foreign amounts are ignored.
- **`readSpendingData`:**
  - It runs one `AbortSignal.timeout(timeoutMs)` for all its requests, in parallel per endpoint, and pages each one
    after another. The requests: the transactions of `range` (`type=all`); `accounts?type=asset`; `categories`;
    `rule-groups`, then the found group's rules; `earliestPostingDate`.
  - For each conflict it calls `warn` with a line naming the category.
  - `mainGroupsFound` is `findRuleGroup(…) !== null`; when it is false every category is in Uden hovedgruppe.
  - The categories in an excluded main group are left out of `categories`.
  - An account a posting refers to that `accounts?type=asset` did not list is added. Its id and name come from the
    split's `source_id`/`source_name` or `destination_id`/`destination_name`. The spike did not check whether
    Firefly III lists inactive accounts, and this keeps D12's promise either way.
- **`earliestPostingDate`** is the spike's two GETs: `transactions?start=1900-01-01&end=<today>&type=all&limit=1&
  page=1`, read `total_pages` N (0 → `null`), then `page=N`. The date is its split's first 10 characters.
- **`readVersion`** reads `about` and returns `data.version`.
