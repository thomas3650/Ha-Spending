# The skeleton – implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an add-on whose page says "Hej" through Home Assistant's ingress, with the repo layout, docs, hard rules,
reviewer, workflows and release path of the technical spec, released once, so the whole path is proven before any
feature (technical spec §11, step 1).

**Architecture:** npm workspaces in `addon/` (`shared`, `server`, `web`). A Hono server on Node 24 serves
`GET /api/health` and the page's built files, and answers only Home Assistant's ingress address. The page is one Lit
element that shows "Hej" and the server's version, fetched with a relative URL. The image is `node:24-alpine` with the
server bundled into one file by esbuild. Workflows, release-please and the image build follow Ha-Fitness, trimmed to
one component.

**Tech Stack:** TypeScript 6.0.3 (strict), Node 24, Hono 4.13.14 + `@hono/node-server` 2.1.5, Lit 3.3.3, Vite 8.3.5,
Vitest 5.0.5, happy-dom 21.0.4, `@testing-library/dom` 10.4.2, ESLint 10.13.0 + typescript-eslint 8.72.0, esbuild
0.28.2, tsx 4.23.15, `@types/node` 24.19.2. The versions of Ha-Fitness's website where it has them.

**Spec:** [technical spec](../specs/2026-10-30-technical-design.md) (§2, §5, §6 first bullets, §7.1, §7.3, §8, §9, §10,
§11 step 1), within the [UI and UX spec](../specs/2026-10-30-ui-ux-design.md) (§3.1: "Forbrug" in the side menu, a
light theme). The template is Ha-Fitness (`~/Documents/Sourcecode/Ha-Fitness`): copy its files where this plan says so,
and trim them; never invent an action SHA.

## Decisions this plan makes (entries for `docs/decisions.md`, Task 5)

- **D1** An add-on with its page in the side menu through ingress; TypeScript on both sides (issue #1, spec header).
- **D2** npm workspaces rooted in `addon/` (spec §2).
- **D3** Hono on `@hono/node-server` (spec §5).
- **D4** The image is `node:24-alpine`, pinned by digest, with the server bundled by esbuild into one file and the
  page's build beside it; no `node_modules` in the image. `init` is left at its default (true), so Docker's init
  passes signals to Node; with no s6-overlay the container's environment (`TZ`) reaches Node as it is. Node 24, not
  the spec's Node 22 (§2, §5): the active LTS, and what Ha-Fitness builds with. Dependabot has no `docker`
  ecosystem here, so the digest is bumped by hand (`docs/releasing.md`). Why: one explicit Node version for build
  and run, and the smallest runtime.
- **D5** Ingress only by the peer address: `172.30.32.2`, also in its IPv4-mapped IPv6 form `::ffff:172.30.32.2`;
  everything else 403. `HA_SPENDING_DEV=1` turns the check off (the fast loop). Port 8099, not published (spec §5).
- **D6** Git hooks are plain scripts in `.githooks/`, set with `git config core.hooksPath .githooks` by
  `scripts/setup`; actionlint and zizmor run through pinned `uvx`; the link check is a Node script. Why: no Python
  toolchain in the repo, the same tools as Ha-Fitness.
- **D7** `addon-image` asks GHCR with `GITHUB_TOKEN` (`packages: read`), not anonymously, so a package that does not
  exist yet reads as missing (404) and the first image builds; anonymously GHCR answers 403 for it (checked
  2026-10-30). The version `0.0.0` is never built. That the package is public is checked by hand
  (`docs/releasing.md`).
- **D8** `panel_title: Forbrug` is Danish in `config.yaml`: the UI spec §3.1 names the side-menu entry, and it wins
  over the technical spec's English-only rule where the two meet.
- **D9** One release component, `addon/`, tagged `vX.Y.Z`, first release `0.1.0` (spec §9).

## Review Focus

- **The peer address as Node reports it:** behind a dual-stack listener the Supervisor's address arrives as
  `::ffff:172.30.32.2`; it must be let in, and `127.0.0.1`, `::1`, `172.30.32.1`, `172.30.32.20` and a request
  with no peer address at all must get 403, not 500 (Task 1 tests; `getConnInfo` throws without a socket, so the
  app catches that and treats it as no address).
- **The page under the ingress prefix:** every asset URL and every fetch is relative (`./web/…`, `api/health`), so the
  page works at `/api/hassio_ingress/<token>/` (Task 2: `check-dist.mjs`, and a test on the fetched URL).
- **The first image:** `addon-image` on a package that does not exist yet builds it; on `0.0.0` it builds nothing
  (Task 4, a shell check of the prepare logic; the authenticated GHCR answer itself was checked by hand on
  2026-10-30: token 200, manifest 404).
- **Release-please reads the PR title:** squash merges with the PR title as the subject; until the repo setting is
  changed (`squash_merge_commit_title` is `COMMIT_OR_PR_TITLE` today), every merge is
  `gh pr merge <n> --squash --subject "<PR title> (#<n>)"` (Task 5 docs, and the controller).
- **Release-please cannot open its PR yet:** the repo has no `RELEASE_PLEASE_TOKEN` and "Allow GitHub Actions to
  create and approve pull requests" is off, so the `release-please` job on `main` fails until Thomas sets one of
  them. Until then the controller runs the release-please CLI with Thomas's `gh` login (After the tasks, step 4),
  and `docs/releasing.md` says so.
- **A request that is not a GET:** `POST /api/health` and any unknown `/api/…` path answer 404 and never 200 (Task 1).
